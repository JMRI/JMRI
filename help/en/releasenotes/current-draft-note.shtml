Dispatcher

  • An automatic train waiting for a stop sensor that never goes active no longer runs on out of its Section at its stopping speed. It is stopped as soon as it enters a free Block beyond the Section, and a train stopping by distance into its destination Section is also stopped when, by reckoning from its speed profile, it reaches the end of the Section. A warning naming the stop sensor is written to the System Console.
  • A Block change that an automatic train handles just after one of its Sections is released, or as the train is terminated, no longer gives warnings such as "No next Block" or that the train has disappeared. The train now uses the direction the Section was allocated in, and ignores Block changes once it is being terminated.
  • Place train name in allocated Blocks no longer writes the train's name into the value of the Blocks Dispatcher allocates, so the train name shown in allocated Blocks is no longer overwritten or lost as trains move. With the option off, the default, nothing changes. With it on, the train a Block is allocated to is kept as the Block's new allocated value, and Block Contents icons and Layout Block memories show it wherever the Block does not already show a train, so panels, including web panels, look as before. A Block Contents Input icon edits the Block's value, so it shows only the value, and is empty in an empty allocated Block. A Logix, LogixNG or script that reads the value of an allocated Block now gets only the train Block tracking has placed there: nothing where the Block is empty, or where Block tracking could not tell which train entered. getDisplayValue() gives what the value gave before, and getAllocatedValue() gives only the train the Block is allocated to; a script that listens for changes to a Block's value to notice allocations should also listen for its allocatedValue property. See the Block Table help. So that anyone whose own script or Logix behaves differently can find out why, Dispatcher logs a note saying this the first time it allocates a Block in a session with the option on. Section.setNameFromActiveBlock, Section.suppressNameUpdate and LayoutBlock.setSuppressNameUpdate are no longer needed; they still work, but log a warning the first time they are used, and will be removed.

LogixNG

  • When a LogixNG is loaded and an item it uses, such as a sensor, is not found, an error now names the missing item in the System Console. Before, the item was silently left empty and shown as ''.
  • Execute action, Last result of digital expression and the Entry/Exit action and expression no longer lose their item when another file is loaded after the item was renamed.
  • A Sequence that doesn't run continuously runs once each time its Start expression becomes true. Before, it started again at once, and on every later event, for as long as Start stayed true, repeating its steps. Start sequence immediately on load now starts it once, too, instead of on every event. In the same way, a Sequence's Reset expression now resets it once each time it becomes true, instead of on every event while it stays true.

Throttle

  • Code and scripts can now be told when each speed or direction command from a throttle has actually been sent to the layout, and when (Throttle.addSpeedSentListener). The time is taken as soon as the command is written to the connection, after any wait for other work or for messages queued ahead of it. CBUS throttles report it, on real CBUS connections and on CAN Simulation; Throttle.reportsSpeedSent() says whether a throttle does. Nothing that listens to a throttle's properties sees anything new.

  • The Turnout and Sensor tables can now add a sequential range of up to 1000 items at once (was 100), e.g. a whole C/MRI node. The confirmation for a large range is unchanged.
  • When the user name of a sensor, turnout or other item is changed from one name to another in any way, for example by a script, the places that use it by that name now follow the change. Before, only a change made in a table window did this, and after storing and reloading, a LogixNG could lose the item.

Miscellaneous

  • Quitting JMRI, and closing the CBUS or LCC Hub window, no longer wait about 2 seconds for each network address while JMRI withdraws its ZeroConf (mDNS) announcements, such as the Hub's, WiThrottle's and the Web Server's. The wait is now about 2 seconds in all.
  • A new window, Tools > Train Tracking > Set-up Checks, lists what in a layout's set-up makes following trains less sure: trains with no length, or no speed profile for their lead loco; Blocks with no length; a detected Block with no paths; a path with no path back; a sensor used by two Blocks; a Block with no detector whose routes depend on a turnout with no feedback; and Blocks joined through Blocks with no detector by more than one way. Each says what is wrong. The checks only read, and change nothing.
  • For developers: a new train record (jmri.TrainRecord, from the jmri.TrainRecordManager) holds what is known about a train from one run to the next: its name, the roster entries of its locos and its ID tags, the parts it is split into or joined from, how it is detected, and its length from each source. Nothing uses it yet, so nothing changes for users.
  • In a profile whose connections are all simulators (the Internal connection, CAN Simulation and the other simulator connections), scripts and tests can now place simulated trains. Driven by the Internal connection's throttles, as Dispatcher, Warrants and throttle windows on that connection do, they move on the layout's own track and set internal sensors as they pass, with the time they passed. The sample script SimulatedTrains.py shows two trains running.
