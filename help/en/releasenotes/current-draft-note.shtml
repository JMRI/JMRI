Dispatcher

  • With "Place train name in allocated Blocks" on, a Block Contents icon now shows the train a Block is allocated to in italics after an arrow, for example → 47012, until Block tracking places the train in the Block, so a dispatcher can see which trains are really in their Blocks. Web panels show it the same way. Icons that use an icon for each value, and Layout Block memories, are unchanged.
  • An automatic train waiting for a stop sensor that never goes active no longer runs on out of its Section at its stopping speed. It is stopped as soon as it enters a free Block beyond the Section, and a train stopping by distance into its destination Section is also stopped when, by reckoning from its speed profile, it reaches the end of the Section. A warning naming the stop sensor is written to the System Console.
  • Terminating an automatic train no longer freezes JMRI. Terminating waited until the train's speed read zero, and if Dispatcher gave the train another Section at that moment the train set its speed again, so the wait never ended. The same could leave that Section allocated to a train that no longer existed, so no other train could have it. A train is now stopped at once when it is terminated, and is given nothing more.
  • For developers: each Active Train now refers to the record of its train (ActiveTrain.getTrainRecord()), found by its roster entry or name, which keeps its Train Detection and Max Train Length and is kept when the Active Train is terminated, so the next Active Train for the same train refers to it again. Nothing users see changes.
  • For developers: a placed train record now follows its train from Block to Block as detection sees it: the Blocks it is in, a trail of the Blocks it entered and when (from the sensor's first report), which end leads, and how sure JMRI is of where it is. Dispatcher places an Active Train's record in its start Block, and a record is placed where a Block's value names it. It only watches: nothing on the layout changes.
  • With automatic allocation, an automatic train is no longer held for good by a meet planned after it had already been given the road beyond its meeting place. Two trains running the same way round a circuit could be taken for trains coming towards each other; one was then told to wait in a station for the other, which needed track the waiting train already held. Dispatcher now drops such a meet, as it does when a train is already past the meeting place.
  • With automatic allocation, an automatic train is no longer held for good in a passing loop or before one, waiting for another train that cannot pass or meet it there. Dispatcher now plans a meet only when the other train has a free track to take, and drops the plan when the train it waits for can no longer get there: the other track is occupied or held by another train, a train has taken the other's track, or a train is already past the meeting place. Allocating by hand was needed to free the train.
  • A Section can have a stop point for each direction, set in the Section's Add/Edit window in mm or in inches (to the nearest 1/32): where the front of a train stops in it, which is where its stopping sensor is if it has one. An automatic train with a speed profile then slows over the distance to the stop point whenever it stops in the Section, at a signal or for want of the next Section as well as at the end of its trip, and stops on the stopping sensor, or at the stop point if there is none. Each Block the front of the train enters, and, for trains whose end is detected, each Block the end of the train leaves, corrects how far it has to go. A stop point beyond the end of its Section is refused there, reported by Validate All Sections, and stops an automatic train being started. Sections without a stop point work as before.
  • A Block change that an automatic train handles just after one of its Sections is released, or as the train is terminated, no longer gives warnings such as "No next Block" or that the train has disappeared. The train now uses the direction the Section was allocated in, and ignores Block changes once it is being terminated.
  • Place train name in allocated Blocks no longer writes the train's name into the value of the Blocks Dispatcher allocates, so the train name shown in allocated Blocks is no longer overwritten or lost as trains move. With the option off, the default, nothing changes. With it on, the train a Block is allocated to is kept as the Block's new allocated value, and Block Contents icons and Layout Block memories show it wherever the Block does not already show a train, so panels, including web panels, look as before. A Block Contents Input icon edits the Block's value, so it shows only the value, and is empty in an empty allocated Block. A Logix, LogixNG or script that reads the value of an allocated Block now gets only the train Block tracking has placed there: nothing where the Block is empty, or where Block tracking could not tell which train entered. getDisplayValue() gives what the value gave before, and getAllocatedValue() gives only the train the Block is allocated to; a script that listens for changes to a Block's value to notice allocations should also listen for its allocatedValue property. See the Block Table help. So that anyone whose own script or Logix behaves differently can find out why, Dispatcher logs a note saying this the first time it allocates a Block in a session with the option on. Section.setNameFromActiveBlock, Section.suppressNameUpdate and LayoutBlock.setSuppressNameUpdate are no longer needed; they still work, but log a warning the first time they are used, and will be removed.
  • Section.setNameInBlocks is no longer used either; it still works, but logs a warning the first time it is used, and will be removed.

  • For developers: a train record now follows its train through Blocks with no detector: when the train reaches the next detected Block through a run of them, along paths that are set, they are added to the Blocks it is in, and they are left when it is seen to leave a detected Block in front of them.   • A new window, Tools > Train Tracking > Set-up Checks, lists what in a layout's set-up makes following trains less sure: trains with no length, or no speed profile for their lead loco; Blocks with no length; a detected Block with no paths; a path with no path back; a sensor used by two Blocks; a Block with no detector whose routes depend on a turnout with no feedback; and Blocks joined through Blocks with no detector by more than one way. Each says what is wrong. The checks only read, and change nothing.
  • Where a train has been placed in a Block (by Dispatcher, or by setting a Block's value to the train), right-clicking the Block's track on a Layout Editor panel in operating mode, or a Block Contents icon, now offers "Block ...". It shows the trains in the Block, how sure JMRI is of where each is, why, and the last 20 things that happened there. The Block Table has Train and "Why?" columns, which can be shown from the column header's menu. A Block Contents icon's double-click still edits the Block's value. Nothing on the layout changes.
  • The Train Tracking help page is now in the help's contents and index, and the Blocks and Block Table help pages link to it.
  • For developers: a new train record (jmri.TrainRecord, from the jmri.TrainRecordManager) holds what is known about a train from one run to the next: its name, the roster entries of its locos and its ID tags, the parts it is split into or joined from, how it is detected, and its length from each source. Nothing uses it yet, so nothing changes for users.
  • The operator can now tell train tracking where trains are: in the Block dialog, choose the train in "Train here" and press Confirm, or press Clear Block when no train is there; on a Layout Editor panel in operating mode, drag a loco marker onto a Block's track. This changes only train tracking's record of the train, not Dispatcher or Warrants. Panels whose items don't control the layout show the dialog without these. JMRI's permissions can limit who may do it (Train tracking: Correct where trains are); everyone may by default.
  • For developers: a new page, Writing Tests with Simulated Trains, explains how to write tests with simulated trains: the test helper and the standard test layouts, why tests assert the order of events and the ground truth rather than durations, truth offsets, and the rule that the simulator never uses the logic it tests.
  • In a profile whose connections are all simulators (the Internal connection, CAN Simulation and the other simulator connections), scripts and tests can now place simulated trains. Driven by the Internal connection's throttles, as Dispatcher, Warrants and throttle windows on that connection do, they move on the layout's own track and set internal sensors as they pass, with the time they passed. The sample script SimulatedTrains.py shows two trains running.
  • For developers: simulated trains can carry an ID tag, read by the reporters of the Blocks they come into, on internal reporters and on CBUS reporters of CAN Simulation connections.
  • For developers: tests and scripts can set faults on simulated trains' layout: detector drop-outs, a sensor showing a train that isn't there, swapped sensors, a Block longer or shorter than JMRI has it, a stalled train and a train that parts. A train whose turnout is moved under it now derails and stays where it stopped.
  • A new help page, Tools: Simulated Trains, describes simulated trains for users: where they can run, how they are driven and seen, the track and trains they use, and how to place them from a script. It is in the help's contents and index, and linked from the Tools and Scripting examples pages.
