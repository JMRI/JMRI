What the simulator is for

JMRI's simulator connections accept speed commands, but on their own nothing moves. Simulated trains add trains that do move. In a profile whose connections are all simulators, a test places a virtual train on a Block. The train then moves on the layout's own track, as its throttle tells it. It sets the Blocks' sensors as it passes, with the time it passed.

This lets a test drive Blocks, Dispatcher, Warrants and scripts with moving trains, without a real layout. The simulator also knows exactly where each train really is. So a test can compare what JMRI concluded with what really happened.

The simulator is in the package jmri.jmrit.simulation. Its Javadoc describes each class.

The test helper and the standard layouts

Two classes in the test tree help tests in any package:

  • jmri.jmrit.simulation.SimulationTestUtil sets up a fully simulated profile with an Internal connection. It makes plain Blocks with internal sensors, places trains, gets throttles to drive them, and waits for and reads the ground truth. Its removeTrains() is for the tear-down.
  • jmri.jmrit.simulation.SimulationTestLayouts builds standard layouts in code, each on its own Layout Editor panel:
    • a loop with a passing loop: an oval with a station, where a main platform road and a loop road run between two turnouts;
    • a terminus: an approach, a throat turnout and two platform roads ending at end bumpers;
    • a junction with a crossover: double track, a crossover between the lines, and a junction turnout leading to a branch line.
    Each has Layout Blocks with internal sensors (IS and the Block's name), internal turnouts (IT and the turnout's name), real lengths in millimetres, and the Block paths JMRI makes after loading a panel. All turnouts start closed. The class Javadoc gives each layout's Blocks and lengths.

SimulationTestLayouts also has made-up locos. Each is written as a roster file, as DecoderPro writes one, with CV3, CV4, CV29 and a speed profile. The simulator reads the momentum CVs and the measured speeds from it.

The layouts are drawn on panels, so tests that use them need a display. Mark them @DisabledIfHeadless. Tests that use only SimulationTestUtil's plain Blocks run headless.

A short example: a train runs from the approach into platform 2 of the terminus.

@DisabledIfHeadless
public class MyTerminusTest {

    private SimulationTestLayout layout;

    @Test
    public void testIntoPlatform2() throws IOException {
        layout.turnout("Throat").setCommandedState(Turnout.THROWN);
        RosterEntry tank = SimulationTestLayouts.rosterEntry(SimulationTestLayouts.Loco.TANK);
        VirtualTrain t = VirtualTrain.builder("Local")
                .loco(SimulatedLoco.builder(tank).length(120).build())
                .length(200).build();
        SimulationTestUtil.place(t, layout.block("Approach"), null, 1200);

        DccThrottle throttle = SimulationTestUtil.throttle(3);
        throttle.setSpeedSetting(0.8f);
        SimulationTestUtil.waitForFrontIn(t, layout.block("Platform2"));
        throttle.setSpeedSetting(0.0f);
        SimulationTestUtil.waitForTruth(tr -> tr.getTrain(t).getSpeedMmPerSecond() == 0.0, "stopped");
        assertEquals(layout.block("Platform2"), SimulationTestUtil.truth(t).getFrontBlock());
    }

    @BeforeEach
    public void setUp(@TempDir File folder) {
        JUnitUtil.setUp();
        SimulationTestLayouts.setUpProfile(folder);
        layout = SimulationTestLayouts.terminus();
    }

    @AfterEach
    public void tearDown() {
        SimulationTestUtil.removeTrains();
        layout.dispose();
        JUnitUtil.deregisterBlockManagerShutdownTask();
        JUnitUtil.tearDown();
    }
}

SimulationTestLayoutsTest has more examples: a train round the loop, into a terminus platform and back out, across the crossover and onto the branch.

Real time: assert order, not durations

Trains in tests move in real time, on the simulator's own thread. Dispatcher, Warrants and the throttles' users run on real timers and threads, so the trains they drive must move on the same clock.

A test machine can be busy, so how long anything takes varies from run to run. A test must therefore not assert durations, and must not sleep. Instead:

  • wait for a condition, with SimulationTestUtil.waitForFrontIn, waitForTruth or JUnitUtil.waitFor;
  • assert the order of events, such as the order in which sensors went active;
  • assert the ground truth: where the train really is, and whether it has stopped.

Only wait in turn for Blocks a train takes seconds to pass. A train may pass a short Block between two looks, and the wait then never ends. Record sensor changes with a listener instead, and check their order afterwards.

The simulator's own tests also run it step by step on a manual clock, so that the times they check are exact. That clock stays inside the package. A test of other JMRI code driven by it would see JMRI's timers and the trains disagree about the time.

Ground truth

SimulatedLayout.getTruth(), or SimulationTestUtil.truth(), gives what is really happening. For each train it gives:

  • its Blocks, from front to rear;
  • how far its front is into its front Block, in millimetres;
  • its speed, negative when it moves rear first;
  • whether it was stopped by a collision, and why it is held if it is.

It also lists every collision: which trains, where and when.

Compare what JMRI concluded with the ground truth. For example, check that the Block Dispatcher thinks a train is in is the Block the train is really in. Or check that the sensors that are active are just the Blocks the trains really occupy.

Truth offsets

Where the simulator and JMRI read the same data, they agree on the data. A Block's length, or a loco's speed profile, is right for both, or wrong for both. A test that uses the data unchanged checks JMRI's code only: its arithmetic, timing, ordering, the Block chosen and the thread used. That is still worth checking. But it can't show whether JMRI copes with data that are wrong.

So a train can be told to differ from what JMRI is told:

  • VirtualTrain.Builder.speedFactorPercent: it runs a set percentage faster or slower than its speed profile;
  • VirtualTrain.Builder.lengthOffsetMm: it is longer or shorter than the length JMRI is given.

A test that claims to check a correction, a calibration or an estimate must set at least one offset, and say which. Examples are a learned speed, a stopping distance, an operator correction, or a train's position between sensors. Without an offset, the test checks JMRI's code only, and it should say so.

The independence rule

A simulator that shares logic with what it tests has the same bug in both places. The two then agree, and a test that compares them passes however wrong both are. So the simulator works things out itself. It never calls the logic under test.

The simulator may read configuration and data:

  • Block (its length and sensor), Path (lengths, and turnout settings as data), Sensor and Turnout;
  • the Layout Editor track objects;
  • OBlock, OBlockManager, OPath and Portal;
  • roster entries, and the speed profile's measured speeds.

It may not use:

  • Dispatcher (jmri.jmrit.dispatcher), Signal Mast Logic and Entry/Exit;
  • Warrants and Tracker: all of jmri.jmrit.logix except OBlock, OBlockManager, OPath and Portal;
  • Block tracking: Block's occupancy, value and direction methods (getState, setState, the going... methods, findFromPath, getValue, setValue, getDirection, setDirection), BeanSetting.check(), Path.checkPathSet() and Path.getLengthMm();
  • Layout Block routing: LayoutBlockConnectivityTools, ConnectivityUtil, LayoutEditorAuxTools, and LayoutTurnout's state and turnout getters;
  • RosterSpeedProfile's calculations (only its stored speeds may be read) and SpeedUtil;
  • a system's own encoding of its messages; for CBUS, CbusAddress and CbusSensor.

A system's adapter, which lives with that system's code, sends the messages a real device on that system would send, and builds them as that system's beans do. Its tests check those messages against tables worked out from the system's own specification, in the test tree and not from JMRI's code, so a fault in JMRI's encoding still shows.

So, on Layout Editor panels, the simulator follows the drawn track itself. It does not use the Block paths JMRI builds from the drawing. A fault in building paths then sends JMRI one way and the train the other, and a test sees it. Momentum comes from the simulator's own decoder model, written from the NMRA standard. Speeds between measured steps are interpolated by the simulator itself.

A rule in ArchitectureTest enforces this on every build. It fails if a class in the simulation package depends on anything in the list above. If you change the simulator, keep to the rule. Don't weaken the rule to get round it.

A second rule works the other way round: the rest of JMRI doesn't use the simulator, so it can't change how JMRI behaves on a real layout. Only the simulator and the packages listed in ArchitectureTest's SIMULATION_USERS may depend on it. A system's adapter is added to that list with its package. Tests are not checked by this rule.

Control Panel Editor panels have no drawn track, only OBlocks and their paths. There the simulator has to use the paths too, so the check is weaker. Tests say which kind of panel they used.

Removing trains

Call SimulationTestUtil.removeTrains() in the tear-down, before JUnitUtil.tearDown(). It removes every train and waits for the simulator's thread to stop. Then close any panel on the GUI thread, for example with SimulationTestLayout.dispose().

Remove trains only after anything driving them has stopped. Terminate Dispatcher's Active Trains and end Warrants first. Removing a train leaves every Block it is in, so their sensors go inactive. Dispatcher or a Warrant still running would see its train leave its Blocks without entering others, and log that the train has gone.
